## User Scenarios & Testing *(mandatory)*

### User Story 1 - GitHub 핸들만으로 식별되는 유저 (Priority: P1)

서비스에 들어온 유저는 GitHub 계정 하나로 식별된다. 화면과 CLI에 보이는 이름은 GitHub 핸들(`login`)이고, 계정을 알아보는 기준은 유저가 바꿀 수 없는 GitHub 숫자 식별자(`github_id`)다. 42 Intra ID와 캠퍼스는 "아직 안 한 추가 인증"이므로 비어 있는 상태가 정상이다.

**Why this priority**: 이 전환 없이는 UI를 포팅할 수 없다. 화면에 어떤 이름을 그릴지, 캠퍼스 뱃지를 그릴지 말지가 정해지지 않은 상태로 컴포넌트를 만들면 조건부 렌더를 두 번 작성한다 (req FR-016 "UI 포팅 선행").

**Independent Test**: 42 정보가 전혀 없는 유저(`intra_id`·`campus`·`intra_verified_at`이 모두 비어 있음)를 만들어 글 작성·참여·목록 조회가 끝까지 되는지 확인한다. 그 유저가 보이는 이름이 GitHub 핸들인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 42 추가 인증을 하지 않은 유저, **When** 계정을 만든다, **Then** GitHub 숫자 식별자와 GitHub 핸들은 반드시 채워져 있고 42 Intra ID·캠퍼스·42 인증 시각은 비어 있다. (TC-IDENT-01)
2. **Given** 같은 GitHub 숫자 식별자, **When** 두 번째 계정 생성을 시도한다, **Then** 중복 계정이 생기지 않는다. (TC-IDENT-01)
3. **Given** 서로 다른 두 유저, **When** 같은 GitHub 핸들을 쓰려 한다, **Then** 거부된다(핸들도 서비스 내에서 유일하다).
4. **Given** 42 추가 인증을 하지 않은 유저, **When** 글 작성·참여·완주 판정을 한다, **Then** 캠퍼스가 비어 있다는 이유로 막히지 않는다.
5. **Given** 전환 이전에 이미 있던 유저 레코드와 그 유저가 쓴 글·참여 기록, **When** 전환을 적용한다, **Then** 글과 참여 기록은 그대로 유저에 연결된 채 남고, 유저마다 GitHub 식별자와 핸들이 채워진다. (TC-IDENT-03)

### User Story 2 - 캠퍼스 없는 유저의 LIVE 핑 (Priority: P1)

캠퍼스 인증을 하지 않은 유저도 "지금 클러스터" LIVE 핑을 올릴 수 있다. 핑의 장소 분류는 작성자 캠퍼스에서 파생되는데, 캠퍼스가 없으면 "그 외 오프라인"으로 기록된다. 등록이 거절되지는 않는다.

**Why this priority**: 캠퍼스를 nullable로 바꾸는 순간 기존 파생 규칙(경산/서울 둘 중 하나)이 깨진다. US1과 같은 PR에서 닫아야 하는 구멍이다 (req FR-016 "캠퍼스 미인증 유저의 LIVE 핑 등록을 차단하지 않는다").

**Independent Test**: 캠퍼스가 비어 있는 유저로 LIVE 핑을 1건 올려 생성이 성공하고 장소 분류가 "그 외 오프라인"으로 저장되는지 확인한다. 캠퍼스를 가진 유저의 파생 결과는 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 캠퍼스가 비어 있는 유저, **When** LIVE 핑을 등록한다, **Then** 201과 함께 핑이 생성되고 장소 분류는 "그 외 오프라인"이다. (TC-IDENT-02)
2. **Given** 캠퍼스가 경산인 유저, **When** LIVE 핑을 등록한다, **Then** 장소 분류는 기존과 같이 "경산 오프라인"이다. (TC-IDENT-02)
3. **Given** 캠퍼스가 서울인 유저, **When** LIVE 핑을 등록한다, **Then** 장소 분류는 기존과 같이 "서울 오프라인"이다. (TC-IDENT-02)
4. **Given** 캠퍼스가 비어 있는 유저, **When** 정규 스터디·단기 파티를 개설한다, **Then** 장소 분류는 유저가 고른 값(온라인/경산/서울/혼합)을 그대로 쓰며 캠퍼스와 무관하다.

### User Story 3 - 조회 응답의 작성자 표기 전환 (Priority: P2)

목록·상세·CLI·명예의 전당·랭킹에서 작성자와 참여자는 GitHub 핸들로 표기된다. 캠퍼스는 "있으면 덧붙는 정보"이고, 없으면 응답에서 비어 있다. 랭킹 동점자 정렬 기준도 GitHub 핸들이다.

**Why this priority**: 화면 포팅(FR-013·FR-019)이 바로 이 응답을 읽는다. 다만 스키마(US1·US2)가 먼저 서야 한다.

**Independent Test**: 캠퍼스 있는 유저와 없는 유저가 섞인 데이터로 5개 조회 응답을 받아, 작성자 이름이 GitHub 핸들이고 캠퍼스가 비어 있는 유저도 정상 표기되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 캠퍼스 있는 유저와 없는 유저가 섞인 목록, **When** 글 목록·글 상세·CLI 목록·명예의 전당·랭킹을 조회한다, **Then** 모든 응답의 유저 표기는 GitHub 핸들이고 캠퍼스는 비어 있을 수 있다. (TC-IDENT-04)
2. **Given** 캠퍼스가 비어 있는 작성자, **When** CLI 텍스트 응답을 본다, **Then** 작성자 표기에 캠퍼스 구분자가 남지 않고 핸들만 보인다. (TC-IDENT-04)
3. **Given** 완주 횟수·리더 횟수가 동률인 유저들, **When** 랭킹을 조회한다, **Then** GitHub 핸들 오름차순으로 순위가 갈리고 공동 순위가 없다. (req FR-010)
4. **Given** 어떤 조회든, **When** 응답을 본다, **Then** 42 Intra ID와 42 인증 시각은 응답에 실리지 않는다.
5. **Given** 비참여자의 글 상세 조회, **When** 응답을 본다, **Then** 채팅 링크 마스킹 동작은 전환 전과 동일하다 (CLAUDE.md §6.2).

### User Story 4 - Mock 페르소나 4종 (Priority: P3)

개발자가 Mock Auth 모달에서 "GitHub 인증만 한 유저"를 1클릭으로 골라, 캠퍼스 뱃지가 비는 화면과 "그 외 오프라인" 핑을 브라우저에서 직접 확인한다.

**Why this priority**: 검증 수단이지 제품 기능이 아니다. 다만 Phase 3 UI 포팅 때 캠퍼스 null 분기를 눌러볼 유일한 방법이다.

**Independent Test**: Mock Auth 모달에서 새 페르소나를 고르면 캠퍼스가 비어 있는 세션 유저가 되고, 그 상태로 LIVE 핑을 올리면 "그 외 오프라인"으로 저장된다.

**Acceptance Scenarios**:

1. **Given** 개발 환경, **When** Mock Auth 모달을 연다, **Then** 페르소나 4종과 로그아웃을 고를 수 있다. (TC-IDENT-05)
2. **Given** 새 페르소나를 고른 세션, **When** 세션 유저를 확인한다, **Then** GitHub 핸들은 채워져 있고 캠퍼스는 비어 있다. (TC-IDENT-05)
3. **Given** 같은 페르소나를 여러 번 고른다, **When** 매번 해석한다, **Then** 같은 유저 레코드가 재사용되고 중복 생성되지 않는다(멱등).
4. **Given** 상용 환경, **When** Mock 경로에 접근한다, **Then** 전환 전과 같이 차단된다 (CLAUDE.md §6.1).

### Edge Cases

- 전환 이전 유저 레코드에는 GitHub 식별자·핸들이 없다. 두 컬럼이 필수가 되므로 기존 행은 42 Intra ID에서 파생한 값으로 채운다. 채우지 않고 필수 제약을 걸면 전환 자체가 실패한다.
- 전환 이전 유저의 42 Intra ID는 Mock 페르소나 문자열(`gs_leader` 등)이라 실제 42 계정이 아니다. 전환 후에도 42 인증 시각은 비어 있어야 하며, "42 인증을 마친 유저"로 오인되지 않아야 한다.
- 장소 분류 열거형에 값을 추가하는 일은 되돌릴 수 없다(전진 전용). 롤백이 필요하면 값을 지우는 대신 쓰지 않는다.
- 캠퍼스를 참조하는 화면·출력은 전부 "비어 있음" 분기를 가져야 한다. 하나라도 빠지면 캠퍼스 없는 유저의 글에서 깨진 표기가 나온다.
- 캠퍼스가 비어 있다는 사실로 기능을 제한하지 않는다. 캠퍼스 기반 피드 분리·필터도 만들지 않는다 (CLAUDE.md §7.2).
- GitHub 핸들은 유저가 바꿀 수 있다. 핸들이 바뀌어도 계정 매칭은 GitHub 숫자 식별자로 하므로 글·참여 기록이 끊기지 않는다. (실제 갱신 경로는 FR-015, Phase 4)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 유저는 GitHub 숫자 식별자(불변, 필수, 유일)와 GitHub 핸들(표시용, 필수, 유일, 변경 가능)을 가져야 한다. (req FR-016, trd §3.2)
- **FR-002**: 유저의 42 Intra ID는 유일하되 비어 있을 수 있어야 한다. 42 추가 인증 착수 전까지 비어 있는 것이 정상 상태다. (req §1.3)
- **FR-003**: 유저의 캠퍼스는 비어 있을 수 있어야 한다. 캠퍼스 값의 종류(경산/서울)는 그대로 보존한다. (req FR-016)
- **FR-004**: 유저는 42 인증 시각을 가질 수 있어야 하며, 42 추가 인증 착수 전까지 항상 비어 있다. (req FR-016)
- **FR-005**: 장소 분류에 "그 외 오프라인"을 추가해야 한다. 기존 4종(온라인/경산 오프라인/서울 오프라인/혼합)의 의미와 저장값은 바뀌지 않는다. (req FR-016)
- **FR-005a**: "그 외 오프라인"은 LIVE 핑 파생 전용 값이어야 한다. 글 개설 입력에서 유저가 고를 수 있는 장소 분류는 기존 4종으로 유지하고, "그 외 오프라인"을 보낸 개설 요청은 거부해야 한다. 유저가 직접 고를 수 있으면 "캠퍼스 미인증 파생"이라는 값의 의미가 사라진다.
- **FR-006**: LIVE 핑의 장소 분류는 작성자 캠퍼스에서 파생하며, 캠퍼스가 비어 있으면 "그 외 오프라인"으로 기록해야 한다. 캠퍼스가 비어 있다는 이유로 등록을 거부하지 않는다. (req FR-011, FR-016)
- **FR-007**: 전환 적용 시 기존 유저 레코드는 GitHub 식별자·핸들이 채워진 상태로 보존되어야 하고, 기존 글·참여 기록의 유저 연결이 끊기지 않아야 한다.
- **FR-008**: 글 목록·글 상세·CLI 목록·명예의 전당·랭킹 응답의 유저 표기는 GitHub 핸들이어야 하며, 캠퍼스는 비어 있을 수 있는 선택 필드여야 한다. (req FR-016, trd §4)
- **FR-009**: 랭킹의 마지막 정렬 기준(완주 횟수·리더 횟수 동률일 때)은 GitHub 핸들 오름차순이어야 한다. (req FR-010)
- **FR-010**: 어떤 조회 응답도 42 Intra ID와 42 인증 시각을 노출하지 않아야 한다.
- **FR-011**: CLI 텍스트 출력은 캠퍼스가 비어 있는 작성자를 핸들만으로 표기해야 하며, 구분자나 빈 괄호 같은 흔적을 남기지 않아야 한다.
- **FR-012**: 개발 환경 Mock 인증은 페르소나 4종을 제공해야 한다. 기존 3종(경산 리더·경산 멤버·서울 멤버)에 캠퍼스가 비어 있는 GitHub 전용 페르소나 1종을 더한다. 페르소나 해석은 멱등해야 한다. (req FR-000 갱신)
- **FR-012a**: 각 페르소나는 GitHub 숫자 식별자와 GitHub 핸들을 갖고, 42 Intra ID는 비어 있어야 한다. 계정 매칭 기준도 GitHub 숫자 식별자다. 페르소나 문자열을 42 Intra ID로 쓰면 42 인증을 마치지 않은 유저가 42 인증 유저로 오인된다.
- **FR-012b**: 페르소나 목록(키·화면 라벨·캠퍼스)은 한 곳에서만 정의되어야 하고, 세션 해석과 개발용 선택 UI가 같은 정의를 읽어야 한다. 목록이 두 곳에 있으면 페르소나를 더할 때 한쪽만 바뀐다.
- **FR-013**: 전환 내용은 스키마 정의 원본(`docs/trd.md` §3.2)과 코드가 일치해야 하며, 정합성 검증이 통과해야 한다. (CLAUDE.md §3)

### Key Entities

- **유저**: 식별자가 3개다. GitHub 숫자 식별자(불변 매칭 키, 필수), GitHub 핸들(표시용, 필수, 변경 가능), 42 Intra ID(추가 인증 전까지 비어 있음). 실사용 경로에서 캠퍼스를 채우는 수단은 42 추가 인증뿐이지만, 개발용 Mock 시드는 캠퍼스를 직접 채운다. 42 인증 시각은 §1.3 착수 전까지 어느 경로에서도 채우지 않는다(req FR-016). 누적 완주·리더 횟수는 전환 대상이 아니다.
- **장소 분류**: 글의 장소 성격을 나타내는 열거형. 온라인·경산 오프라인·서울 오프라인·혼합에 "그 외 오프라인"이 추가된다. 저장 가능한 값은 5종이지만 유저가 입력할 수 있는 값은 기존 4종이다. 전진 전용으로, 추가한 값은 되돌릴 수 없다.
- **Mock 페르소나**: 개발 환경 전용 고정 유저 정의. 키·화면 라벨·캠퍼스를 갖는 데이터이며 저장소를 알지 못한다. 3종에서 4종으로 늘고, 새 1종은 캠퍼스가 비어 있다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 42 정보가 전혀 없는 유저가 글 작성·참여·LIVE 핑 등록·완주 판정을 끝까지 수행할 수 있고, 캠퍼스가 없다는 이유로 거부되는 요청이 0건이다.
- **SC-002**: 캠퍼스가 비어 있는 유저의 LIVE 핑 100%가 "그 외 오프라인"으로 저장되고, 캠퍼스를 가진 유저의 파생 결과는 전환 전과 100% 동일하다.
- **SC-003**: 5개 조회(글 목록·글 상세·CLI 목록·명예의 전당·랭킹) 응답에서 유저 표기가 GitHub 핸들로 통일되고, 42 Intra ID 노출이 0건이다.
- **SC-004**: 전환 적용 후 기존 유저·글·참여 기록의 건수가 전환 전과 같고, 유저 연결이 끊긴 글·참여 기록이 0건이다.
- **SC-005**: 개발자가 Mock Auth 모달 클릭 1번으로 캠퍼스 없는 유저 세션으로 전환할 수 있다.
- **SC-006**: 인수 테스트 TC-IDENT-01~05가 모두 통과하고, 스키마 정합성 검증(`pnpm drizzle-kit check`)과 기존 테스트 전체가 통과한다.

## Assumptions

- 전환 대상 데이터는 개발용 Supabase 인스턴스의 Mock·테스트 잔여 레코드뿐이다(측정값: 유저 3건, 글 3건, 참여 6건). 실사용자 데이터는 없다.
- 기존 유저의 GitHub 식별자·핸들은 42 Intra ID에서 파생해 채운다. Mock 페르소나에서 나온 값이므로 실제 GitHub 계정과 충돌하지 않는다. Phase 4 OAuth 로그인 시 실제 GitHub 식별자로 매칭되는 계정은 새로 만들어진다.
- 42 Intra ID는 컬럼으로 남지만 어떤 조회 응답에도 싣지 않는다. 42 추가 인증이 §1.3 보류이므로 값을 채우는 경로도 이 전환에 없다.
- 캠퍼스 뱃지의 최종 형태는 §1.3에서 확정된다. 그때 42 Intra ID를 뱃지에 쓰기로 하면 저장소 변경 없이 공개 투영에 필드를 더하면 된다(컬럼은 이 전환에서 만든다). 다만 노출 범위는 **엔드포인트별로** 결정한다 — `GET /api/list`는 인증 없는 공개 엔드포인트이고 작성자 표기와 LIVE 핑의 물리적 위치를 함께 싣기 때문에, 실제 42 핸들을 여기에 더하면 외부인이 특정 카뎃의 위치를 추적할 수 있다(`NFR-005` 최우선 대상). 전체 응답 일괄 추가는 하지 않는다.
- 응답 필드 이름은 `intraId`에서 `login`으로 바꾼다. 이 응답을 읽는 클라이언트는 아직 없고(화면은 Phase 3에서 포팅), CLI는 같은 PR에서 함께 고친다. 과도기 호환을 위해 두 필드를 병행 노출하지 않는다.
- CLI 작성자 표기는 캠퍼스가 있으면 `(핸들·캠퍼스)`, 없으면 `(핸들)`로 한다. 빈 구분자를 남기지 않기 위한 선택이며 다른 출력 형식은 바꾸지 않는다.
- 42 추가 인증, 캠퍼스 뱃지 렌더, 기수 표기, 42 전용 기능 게이팅은 이 전환의 범위 밖이다 (req §1.3). 이 전환은 뱃지를 그릴 수 있는 데이터 조건(캠퍼스 nullable)까지만 만든다.
- 새 인수 테스트 ID TC-IDENT-01~05는 `docs/requirement.md` §3에 함께 추가한다. 요구사항 ID 체계의 SSOT가 그 문서이기 때문이다 (CLAUDE.md §1).
- 유저 식별 컬럼이 늘어도 화면은 외부 프로필 이미지를 수집·저장하지 않는다. 표시는 핸들 앞 2자리 이니셜 뱃지를 쓴다 (CLAUDE.md §7.2).
- 필수 식별자 2개를 기존 행이 있는 테이블에 추가하므로, 전환은 "컬럼 추가 → 기존 행 채우기 → 필수·유일 제약 적용" 순서를 한 번에 적용해야 한다. 제약을 먼저 걸면 전환이 실패한다 (FR-007).
- 장소 분류에 값을 추가하는 전환과 그 값을 쓰는 동작은 분리한다. 값 추가와 사용을 한 단위로 묶으면 저장소가 거부한다.
