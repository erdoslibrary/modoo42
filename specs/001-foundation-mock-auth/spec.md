# Feature Specification: Phase 0 — 기반 인프라 & Mock 인증

**Feature Branch**: `001-foundation-mock-auth`

**Created**: 2026-10-18

**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 페르소나 전환으로 즉시 테스트 (Priority: P1)

개발자가 로컬에서 실제 42 로그인 없이 화면 우하단의 `[🛠 Mock Auth]` 플로팅 모달을
열고, 페르소나(`gs_leader`, `gs_member`, `seoul_member`) 또는 로그아웃(`guest`)을 한 번
클릭해 현재 세션 유저를 즉시 바꾼다. 이후 모든 화면과 API 요청은 전환된 유저의
자격으로 동작한다.

**Why this priority**: Phase 1 이후의 모든 기능(개설·참여·권한)은 "누가 요청했는가"에
의존한다. 실제 OAuth(Phase 4) 없이도 서로 다른 유저 맥락을 재현할 수 있어야 나머지
개발과 TDD가 가능하다. 이것이 Phase 0의 핵심 가치다.

**Independent Test**: 로컬 개발 서버에서 모달을 열어 `gs_leader`를 고르면 세션 유저가
`gs_leader`로 바뀌고, `guest`를 고르면 비로그인 상태가 된다. 다른 기능 없이 이 전환만으로
검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 로컬 개발 환경에서 비로그인(`guest`) 상태일 때, **When** Mock 모달에서
   `gs_leader`를 클릭하면, **Then** 세션 유저가 `gs_leader`로 교체되고 페이지가 즉시
   갱신되어 로그인 유저 정보가 보인다.
2. **Given** `gs_leader`로 로그인된 상태일 때, **When** 모달에서 로그아웃(`guest`)을
   클릭하면, **Then** 세션이 비워지고 비로그인 상태로 돌아간다.
3. **Given** 세 페르소나 각각으로 전환했을 때, **When** 현재 유저 정보를 조회하면,
   **Then** 각 페르소나에 해당하는 고정 유저 레코드(캠퍼스 뱃지 포함)가 반환된다.

---

### User Story 2 - 상용 환경에서 Mock 인증 차단 (Priority: P1)

Mock 인증은 개발 환경에서만 존재한다. 상용 빌드에서는 Mock 모달 UI가 렌더링되지 않고,
Mock 세션 주입 요청도 거부된다.

**Why this priority**: Mock 인증이 상용에 노출되면 누구나 임의 유저로 로그인하는 인증
우회가 된다. 이는 보안 결함이므로 Phase 0에서부터 막아야 하며, 늦게 덧붙일 수 없다.

**Independent Test**: 상용 모드로 빌드·구동한 뒤 Mock 모달이 화면에 없고, Mock 세션
주입 요청이 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 상용 환경으로 구동된 앱일 때, **When** 아무 화면을 열면, **Then** Mock 모달
   UI가 어디에도 나타나지 않는다.
2. **Given** 상용 환경일 때, **When** Mock 세션 주입을 요청하면, **Then** 요청이 거부되고
   세션이 바뀌지 않는다.

---

### User Story 3 - 데이터 모델과 개발 도구 준비 (Priority: P2)

Phase 1 이후 기능이 데이터를 저장하고 TDD 루프를 돌릴 수 있도록, 핵심 데이터 모델
(유저·게시글·참여)과 개발 도구(테스트 러너, 스키마 마이그레이션, 입력 검증, DB 접속
설정)가 갖춰진다.

**Why this priority**: 기능 구현의 토대다. 그 자체로 사용자 가치를 내지는 않지만, 이것
없이는 Phase 1을 시작할 수 없다. 페르소나 전환(US1)보다 뒤지만 반드시 필요하다.

**Independent Test**: 마이그레이션을 적용하면 유저·게시글·참여 저장소가 생성되고, 빈
테스트 스위트가 설정된 DB 접속으로 통과하며, 스키마 정합성 검증이 통과한다.

**Acceptance Scenarios**:

1. **Given** 깨끗한 데이터베이스일 때, **When** 마이그레이션을 적용하면, **Then** 유저·
   게시글·참여 저장소가 생성되고 스키마 정합성 검증이 통과한다.
2. **Given** 개발 도구가 설정된 상태일 때, **When** 테스트 러너를 실행하면, **Then**
   설정된 DB 접속으로 붙어 트랜잭션 격리 하에 테스트가 실행된다.
3. **Given** 세 페르소나 레코드가 유저 저장소에 존재할 때, **When** 유저를 조회하면,
   **Then** `gs_leader`, `gs_member`, `seoul_member`가 각자의 캠퍼스·식별자와 함께 조회된다.

---

### Edge Cases

- 알 수 없는 페르소나 값으로 Mock 세션을 요청하면 어떻게 되는가? → 거부하고 세션을
  바꾸지 않는다.
- 세션 쿠키가 없거나 손상되었을 때 현재 유저 조회는 어떻게 되는가? → 비로그인
  (`guest`)으로 간주하고 오류를 던지지 않는다.
- 상용 환경에서 Mock 세션 쿠키가 수동으로 심어진 경우에도 Mock 인증이 활성화되는가?
  → 아니다. 환경 가드가 서버·클라이언트 양쪽에서 Mock 경로를 차단한다.
- 마이그레이션을 두 번 적용하면? → 이미 적용된 마이그레이션은 재적용되지 않고 정합성
  검증이 통과한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 개발 환경에서 세 페르소나(`gs_leader`, `gs_member`,
  `seoul_member`)와 로그아웃(`guest`) 상태를 한 번의 클릭으로 전환하는 Mock 인증 수단을
  제공해야 한다. (요구사항 FR-000)
- **FR-002**: 시스템은 화면 우하단에 플로팅 `[🛠 Mock Auth]` 모달을 제공하고, 페르소나
  선택 시 세션을 세팅한 뒤 페이지를 즉시 갱신해야 한다.
- **FR-003**: 시스템은 현재 세션에서 로그인 유저를 식별하는 단일 조회 수단을 제공하고,
  세션이 없으면 비로그인으로 취급해야 한다.
- **FR-004**: 시스템은 Mock 인증 UI와 Mock 세션 주입 경로를 상용 환경에서 비활성화해야
  한다. 이 차단은 서버와 클라이언트 양쪽에서 강제되어야 한다.
- **FR-005**: 시스템은 알 수 없는 페르소나 값에 대한 Mock 세션 주입 요청을 거부하고
  기존 세션을 유지해야 한다.
- **FR-006**: 시스템은 유저·게시글·참여 데이터 모델을 정의하고, 이를 생성하는
  마이그레이션과 스키마 정합성 검증을 제공해야 한다.
- **FR-007**: 시스템은 세 페르소나에 대응하는 고정 유저 레코드(식별자, 캠퍼스 구분
  포함)를 제공해, 전환 즉시 해당 유저로 동작하게 해야 한다.
- **FR-008**: 시스템은 핵심 도메인 테스트를 실행하는 테스트 러너와, 설정된 DB 접속으로
  붙는 테스트 환경을 제공해야 한다. 테스트 격리는 트랜잭션 롤백으로 한다.
- **FR-009**: 시스템은 후속 Phase의 입력 검증을 위한 검증 수단과, 공통 오류를 HTTP로
  매핑하는 오류 규약의 토대를 제공해야 한다.
- **FR-010**: 시스템은 외부 프로필 이미지를 수집·저장하지 않고, 식별자 앞 2자리 영문
  대문자 이니셜로 유저를 표기해야 한다.

### Key Entities

- **유저(User)**: 플랫폼 참여자. 식별자(intra_id), 캠퍼스 구분(GS/SEOUL 뱃지),
  리더 완주 횟수·멤버 완주 횟수 집계를 가진다. 외부 프로필 이미지는 저장하지 않는다.
- **게시글(Post)**: 모집 글(스터디·단기 파티·LIVE 핑)의 저장 단위. Phase 0에서는 모델과
  저장소만 마련하고, 생성·참여 로직은 Phase 1에서 구현한다.
- **참여(Participant)**: 유저와 게시글의 참여 관계. Phase 0에서는 모델과 저장소만 마련한다.
- **Mock 세션(Mock Session)**: 개발 환경 전용 페르소나 세션 표식. 쿠키에 선택된 페르소나를
  담아 현재 유저를 결정한다. 상용에서는 존재하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개발자가 Mock 모달에서 페르소나를 선택하면 1회 클릭으로 세션 유저가
  전환되고 화면이 갱신된다.
- **SC-002**: 세 페르소나와 로그아웃을 포함한 4개 상태 모두 전환이 성공한다 (전환
  성공률 100%).
- **SC-003**: 상용 빌드에서 Mock 모달이 노출되지 않고 Mock 세션 주입이 100% 거부된다.
- **SC-004**: 깨끗한 데이터베이스에 마이그레이션을 적용하면 유저·게시글·참여 저장소가
  생성되고 스키마 정합성 검증이 통과한다.
- **SC-005**: 테스트 러너가 설정된 DB 접속으로 실행되어, Phase 1의 TDD(Red-Green-Refactor)
  루프를 시작할 수 있는 상태가 된다.

## Assumptions

- Phase 0 사용자는 로컬에서 작업하는 개발자다. 최종 멤버 대상 UI 가치는 Phase 1 이후에
  나온다.
- 테스트와 마이그레이션이 붙을 PostgreSQL 데이터베이스 접속 정보가 환경변수로 제공된다
  (공용 인스턴스이며 테이블 TRUNCATE 없이 트랜잭션 롤백으로 격리).
- 실제 42 OAuth 연동은 범위 밖이며 Phase 4에서 다룬다. Phase 0은 Mock 인증만 제공한다.
- 게시글·참여의 생성·조회·참여 로직은 범위 밖이다. Phase 0은 모델과 저장소 준비까지다.
- 캠퍼스는 뱃지 표기용이며 피드를 캠퍼스로 분리·필터링하지 않는다.
