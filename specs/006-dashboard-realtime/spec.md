## User Scenarios & Testing *(mandatory)*

### User Story 1 - 대시보드에서 지금 열려 있는 모임을 한 화면에 본다 (Priority: P1)

로그인한 42 멤버가 대시보드를 열면 네 가지 흐름이 한 화면에 보인다. 지금 클러스터에서 당장 사람을 찾는 LIVE 핑 전광판, 마감이 임박한 단기 파티 가로 줄, 이번 사이클 모집 중인 정규 스터디 그리드, 그리고 아래쪽 아카이브(🏆명예의 전당 / 🪦Post-mortem)와 성실 멤버 랭킹이다. 카드마다 제목·태그·리더 핸들·이니셜 뱃지·인원(`4/6명`)이 보이고, 파티는 D-Day, LIVE 핑은 남은 시간이 보인다.

**Why this priority**: 이 화면이 없으면 Phase 1~2에서 만든 모집·참여·완주 API를 쓸 수 있는 사람이 없다. 제품의 유일한 입구다 (req FR-013).

**Independent Test**: Mock 세션으로 로그인해 정규 스터디·단기 파티·LIVE 핑·완주 스터디가 섞인 데이터를 넣고 대시보드를 연다. 네 영역이 각자의 정렬 기준으로 렌더되고, 만료된 LIVE 핑과 취소된 글이 피드에 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 모집 중 정규 스터디 여러 건, **When** 대시보드를 연다, **Then** 정규 스터디 그리드에 카드가 최신순으로 보이고 `[최신순]`/`[마감임박순]` 중 하나를 고르면 그 순서로 다시 그려진다. (req FR-013)
2. **Given** 마감일이 다른 단기 파티 여러 건, **When** 대시보드를 연다, **Then** 마감이 가까운 순서로 가로 줄에 보이고 각 카드에 `D-3` 형태의 남은 일수가 보인다.
3. **Given** 유효시간이 남은 LIVE 핑과 이미 만료된 LIVE 핑, **When** 대시보드를 연다, **Then** 유효한 핑만 전광판에 보이고 각 핑에 남은 시간이 보인다. 만료된 핑은 보이지 않는다. (req FR-011 Lazy Filter)
4. **Given** 내가 올린 LIVE 핑, **When** 전광판을 본다, **Then** 내 핑에만 `[완료]`가 보이고 누르면 그 핑이 전광판에서 사라진다. 남의 핑에는 `[완료]`가 없다.
5. **Given** 완주한 정규 스터디와 회고가 등록된 정규 스터디, **When** 아카이브의 두 탭을 번갈아 고른다, **Then** 🏆명예의 전당 탭에는 완주 스터디와 결과물 링크가, 🪦Post-mortem 탭에는 회고가 보인다. 단기 파티는 어느 탭에도 없다. (req FR-010)
6. **Given** 완주·리더 횟수가 쌓인 유저들, **When** 성실 멤버 랭킹을 본다, **Then** 1~5위가 핸들·누적 완주 횟수·누적 리더 횟수와 함께 보인다.
7. **Given** 어떤 카드든, **When** 리더가 캠퍼스 인증을 하지 않은 유저다, **Then** 캠퍼스 뱃지 자리는 비어 있고 레이아웃이 깨지지 않는다. (req FR-016, FR-019)
8. **Given** 피드가 비어 있는 상태, **When** 대시보드를 연다, **Then** 각 영역에 "첫 번째 리더가 되어 보세요" 같은 빈 상태 안내와 개설 입구가 보인다.
9. **Given** 마감일이 이미 지난 단기 파티, **When** 대시보드를 연다, **Then** 그 파티는 모집 피드에 보이지 않는다. 마감일이 남은 파티와 정규 스터디는 그대로 보인다. (req FR-020, TC-PARTY-01)

### User Story 2 - 상세를 확인하고 두 단계를 거쳐 참여한다 (Priority: P1)

카드의 `[상세보기 ↗]`를 누르면 상세 모달이 열린다. 비참여자도 소개·기간·사이클·진행 방식·장소·참여자 목록·소통 플랫폼 종류·참고 링크를 본다. 실제 초대 링크는 보이지 않는다. `[참여하기]`를 누르면 "정말 참여하시겠습니까? 참여 후에는 취소가 불가능하며 오픈채팅방으로 이동합니다." 확인 팝업이 뜨고, 확정하는 순간 참여가 기록되고 새 탭으로 초대 링크가 열린다. 이미 참여한 유저에게는 `[오픈채팅 바로가기 ↗]`가 고정으로 보인다.

**Why this priority**: 참여는 이 제품의 핵심 전환 동작이고, 2단계 확인과 링크 가시성은 타협할 수 없는 규칙이다 (CLAUDE.md §6.2, 헌법 V).

**Independent Test**: 비참여자 세션으로 상세 모달을 열어 초대 링크가 어디에도 없음을 확인한 뒤 참여를 끝까지 수행하고, 같은 글을 다시 열어 링크 재열람 버튼이 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 비참여자 세션, **When** 상세 모달을 연다, **Then** 소개·기간·사이클·진행 방식·장소·참여자 목록·소통 플랫폼 배지·참고 링크가 보이고 초대 링크는 화면과 전달 데이터 어디에도 없다. (req FR-013, 헌법 V)
2. **Given** 상세 모달, **When** `[참여하기]`를 누른다, **Then** 취소 불가와 외부 이동을 알리는 확인 팝업이 뜨고, 이 단계까지는 아무것도 기록되지 않는다. (prd §1.1 2단계)
3. **Given** 확인 팝업, **When** `[확인]`을 누른다, **Then** 참여가 기록되고 인원이 1 늘어나며 새 탭으로 초대 링크가 열린다. (req FR-003)
4. **Given** 확인 팝업, **When** `[취소]`를 누르거나 팝업을 닫는다, **Then** 참여가 기록되지 않고 상세 모달로 돌아온다.
5. **Given** 이미 참여한 글, **When** 상세 모달을 연다, **Then** `[참여하기]` 대신 `[오픈채팅 바로가기 ↗]`가 보이고 누르면 링크만 열린다. 자진 취소 수단은 어디에도 없다. (req §1.2)
6. **Given** 정원이 찬 글, **When** 비참여자가 상세 모달을 연다, **Then** 참여 버튼이 `[모집 완료]` 비활성 상태로 보인다. (req FR-004)
7. **Given** 취소된 글 또는 완주 판정이 끝난 글, **When** 상세 모달을 연다, **Then** 그 상태가 표시되고 참여 수단이 제공되지 않는다. (req NFR-003)
8. **Given** 확인 팝업에서 `[확인]`을 빠르게 두 번 누른다, **When** 요청이 처리된다, **Then** 인원은 1만 늘고 중복 참여 기록이 생기지 않는다. (req FR-003 멱등성)
9. **Given** 리더 본인 세션, **When** 자기 글의 상세 모달을 연다, **Then** `[수정하기]`·`[스터디 취소]` 관리 입구가 보이고 리더가 아닌 유저에게는 보이지 않는다. (req FR-006, FR-017)
10. **Given** 마감일이 지난 단기 파티, **When** 상세 모달에서 참여를 시도한다, **Then** 참여가 기록되지 않고 마감 안내가 보인다. 상세 내용 자체는 계속 열람할 수 있다. (req FR-020, TC-PARTY-02)

### User Story 3 - 유형에 맞는 폼으로 모임을 연다 (Priority: P2)

개설 화면에서 유형을 고르면 그 유형에 맞는 폼만 나온다. 정규 스터디는 템플릿 버튼 6종으로 제목·태그·설명이 미리 채워지고 종료일은 시스템이 정한 값이 안내로만 보인다. 단기 파티는 마감일을 직접 고른다. LIVE 핑은 한 줄 내용·위치·유효시간 3개만 받는다. 잘못된 입력은 보내기 전에 걸리고, 그래도 서버가 거절하면 그 이유가 화면에 보인다.

**Why this priority**: 피드에 올릴 글을 만드는 유일한 경로다. 다만 US1·US2가 없으면 만든 글을 볼 데가 없으므로 뒤에 둔다 (req FR-013, FR-002).

**Independent Test**: 세 가지 유형으로 각각 한 건을 개설해 대시보드에 그 글이 나타나는지 확인한다. 제목 41자·정원 11명·허용되지 않은 초대 링크·태그 4개를 넣어 거절되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 개설 화면, **When** 유형을 정규 스터디·단기 파티·LIVE 핑 중에서 바꾼다, **Then** 그 유형의 입력 항목만 보인다. (designs: `create_study.html` / `create_study_party.html` / `create_study_live.html`)
2. **Given** 정규 스터디 폼, **When** 템플릿 버튼(코딩테스트·모각코·책 완독·듀오링고·음악 감상·자유)을 누른다, **Then** 기본 제목·설명·태그가 채워지고 수정할 수 있다. (req FR-002, FR-007)
3. **Given** 정규 스터디 폼, **When** 종료일 영역을 본다, **Then** 시스템이 정한 종료일이 읽기 전용 안내로 보이고 직접 고를 수 없다. (CLAUDE.md §7.2)
4. **Given** 단기 파티 폼, **When** 마감일을 고른다, **Then** 달력에서 직접 지정할 수 있다.
5. **Given** 어떤 폼이든, **When** 제한을 넘는 입력(제목 41자, 설명 301자, 태그 4개, 정원 1명 또는 11명, LIVE 내용 51자, 화이트리스트 밖 초대 링크)을 보낸다, **Then** 글이 만들어지지 않고 어떤 항목이 왜 거절됐는지 화면에 보인다. (req FR-001, NFR-002)
6. **Given** 오늘 이미 LIVE 핑을 올린 유저, **When** 두 번째 LIVE 핑을 올리려 한다, **Then** 하루 1회 제한 안내가 보이고 등록이 되지 않는다. (req FR-011)
7. **Given** 개설 성공, **When** 화면이 전환된다, **Then** 대시보드에서 그 글을 볼 수 있고 개설자는 첫 참여자로 잡혀 인원이 `1/N명`으로 시작한다. (req FR-001)

### User Story 4 - 새로고침 없이 지금 상태를 본다 (Priority: P2)

대시보드를 열어 둔 채 다른 사람이 참여하거나 LIVE 핑을 올리면, 화면을 건드리지 않아도 1초 안에 인원 숫자가 올라가고 새 핑이 전광판 맨 앞에 붙는다. 정원이 차서 마감된 글은 그 자리에서 마감 표시로 바뀐다.

**Why this priority**: "지금 클러스터"라는 제품 전제가 실시간성에 걸려 있다. 다만 피드가 먼저 그려져야 붙일 자리가 생긴다 (req FR-014, NFR-004).

**Independent Test**: 브라우저 두 개를 열어 한쪽에서 참여·LIVE 핑 등록을 하고, 다른 쪽이 새로고침 없이 1초 안에 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 대시보드를 열어 둔 유저, **When** 다른 유저가 같은 글에 참여한다, **Then** 1초 안에 그 카드의 인원 숫자가 새로고침 없이 올라간다. (req NFR-004)
2. **Given** 대시보드를 열어 둔 유저, **When** 다른 유저가 LIVE 핑을 올린다, **Then** 1초 안에 전광판 맨 앞에 그 핑이 내용·위치·남은 시간까지 채워진 채로 붙는다.
3. **Given** 마지막 한 자리가 남은 글, **When** 다른 유저가 그 자리를 채운다, **Then** 열어 둔 화면의 카드가 마감 상태로 바뀌고 참여 입구가 닫힌다. (req FR-004)
4. **Given** 작성자가 LIVE 핑을 조기 완료한다, **When** 다른 유저가 전광판을 보고 있다, **Then** 그 핑이 1초 안에 전광판에서 사라진다. (req FR-011)
5. **Given** 실시간 연결이 끊긴 상태, **When** 유저가 대시보드를 계속 본다, **Then** 화면이 깨지거나 비워지지 않고 마지막으로 받은 내용이 유지되며, 새로고침하면 최신 상태가 보인다.
6. **Given** 실시간으로 전달되는 변경 알림, **When** 그 내용을 확인한다, **Then** 초대 링크는 어떤 경로로도 전달되지 않는다. (trd §5, 헌법 V)

### User Story 5 - 내 기록을 확인한다 (Priority: P3)

사이드바 아래 프로필을 누르면 내 화면이 열린다. GitHub 핸들과 이니셜 뱃지, 누적 완주 횟수, 누적 리더 횟수, 그리고 참여한 스터디 이력이 완주·리더·진행 중으로 나뉘어 보인다. 캠퍼스 인증을 했다면 캠퍼스 뱃지가 덧붙는다.

**Why this priority**: 완주 판정의 결과를 유저가 확인하는 유일한 화면이지만, 모집·참여 루프가 없으면 채울 내용이 없다 (req FR-019, prd MoSCoW P1).

**Independent Test**: 완주·리더·진행 중 이력이 섞인 유저로 프로필을 열어 세 구분이 실제 참여 기록과 일치하는지, 카운트가 완주 판정 결과와 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 유저, **When** 프로필을 연다, **Then** GitHub 핸들, 핸들 앞 2자리 이니셜 뱃지, 누적 완주 횟수, 누적 리더 횟수가 보인다. (req FR-019)
2. **Given** 캠퍼스가 비어 있는 유저, **When** 프로필을 연다, **Then** 캠퍼스 뱃지가 렌더되지 않고 기수 표기도 없다. (req FR-016, §1.3)
3. **Given** 완주·리더·진행 중 이력이 섞인 유저, **When** 스터디 이력을 본다, **Then** 각 글이 완주/리더/진행 중으로 구분되어 실제 참여 기록과 같은 목록으로 보인다.
4. **Given** 외부 프로필 이미지, **When** 프로필 화면을 본다, **Then** 어떤 외부 이미지도 불러오지 않고 이니셜 뱃지만 쓴다. (CLAUDE.md §7.2)
5. **Given** 디자인 원본의 개구리 도감·획득 배지 섹션, **When** 프로필을 본다, **Then** 그 두 섹션은 화면에 없다. (req §1.3)
6. **Given** 이력이 하나도 없는 유저, **When** 프로필을 연다, **Then** 빈 상태 안내가 보이고 카운트는 0으로 보인다.

### Edge Cases

- **비로그인(`guest`) 상태의 대시보드 접근:** 조회 API가 인증을 요구하므로 피드를 채울 수 없다. Phase 3에는 랜딩 게이트(`FR-015`, Phase 4)가 없으므로, 빈 화면 대신 "로그인이 필요하다"는 안내와 개발용 Mock 전환 입구를 보여준다.
- **LIVE 핑의 남은 시간이 화면에서 0이 되는 순간:** 만료는 상태 전이가 아니라 조회 필터다. 카운트다운이 0에 닿은 핑은 화면에서 제거하되, 서버에 만료 요청을 보내지 않는다 (CLAUDE.md §6.4).
- **실시간 변경 알림에 제목·위치가 없다:** 공개 복제 컬럼이 최소 집합으로 고정돼 있어 새 LIVE 핑의 내용·태그·위치는 알림에 실리지 않는다. 알림을 받은 뒤 조회로 보강해야 하며, 보강 실패 시 핑을 반쪽짜리로 그리지 않는다 (trd §5).
- **새 탭 팝업 차단:** 참여는 성공했는데 브라우저가 새 탭을 막은 경우, 참여자는 상세 모달의 링크 재열람 수단으로 들어갈 수 있어야 한다.
- **참여 직후 다른 사람이 마지막 자리를 채운 경우:** 확인 팝업을 띄워 둔 사이 정원이 차면 확정 시 정원 초과로 거절된다. 이때 화면은 실패 사유를 보여주고 카드 상태를 마감으로 갱신한다.
- **캠퍼스 뱃지와 기수 표기:** 디자인 원본에 `42경산 · 2기`로 적혀 있으나 기수를 담을 컬럼이 없다. 캠퍼스만 표출하고 기수는 생략한다 (req §1.3).
- **긴 제목·태그 3개·긴 장소 텍스트:** 카드 레이아웃이 밀리거나 겹치지 않아야 하고, 가로 스크롤 영역 밖으로 내용이 삐져나오지 않아야 한다.
- **모바일 폭(375px):** 3열 그리드가 1열로 접히고 가로 스크롤 영역은 손가락으로 밀 수 있어야 한다 (prd F0-3).
- **단기 파티의 마감일이 지났는데 상태가 `RECRUITING`인 글:** 모집 피드에서 제외하고 참여를 거절한다. 상태값은 전이시키지 않고 만료용 배치도 두지 않는다 (req FR-020, 결정 근거는 next-steps §3.3). 상세 조회는 계속 열어 두고 마감으로 표시한다.
- **마감일이 지난 단기 파티에 참여 요청이 들어온 경우:** 상태값이 `RECRUITING`으로 남아 있으므로 상태 검증만으로는 통과한다. 참여 경로에 마감일 검증을 따로 두어 400으로 거절해야 한다 (req FR-020, TC-PARTY-02).
- **완주 판정·Post-mortem 등록 화면(`complete.html`·`complete_postmortem.html`):** 이 브랜치의 범위가 아니다. `FR-021`로 분리해 006 머지 후 별도 브랜치에서 리더 액션 묶음으로 포팅한다. 006의 상세 모달은 그 입구 자리를 비워 두고, 없는 화면으로 가는 버튼을 노출하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**화면 기반 (디자인 시스템)**

- **FR-001**: 모든 화면은 정의된 디자인 토큰(배경 `#EDEFE0`, 텍스트·경계선 `#18181b`, 액센트 `#5FB63A`, 보조 텍스트 `#71717a`, 테두리 2.5px, blur 0 하드 섀도우)을 한 곳에서 참조해야 한다. 화면마다 색을 다시 정의하지 않는다. (CLAUDE.md §10)
- **FR-002**: 타이틀·로고는 Galmuri11, 본문은 Pretendard를 써야 한다. 현재 쓰이는 기본 폰트(Geist·Arial 계열)는 남기지 않는다. (CLAUDE.md §10)
- **FR-003**: 누름 상태의 이동 거리는 그 요소의 하드 섀도우 offset과 같아야 하며, 깊이 값은 한 곳에서 정의하고 사용처에서 덮어써야 한다. 호버는 배경·글자색 변화만 쓴다. (designs/interactions.md §3)
- **FR-004**: 그라데이션·컬러 그림자·`blur ≥ 20px`·배경 장식·호버 시 이동·로드 시 fade 또는 stagger를 쓰지 않아야 한다. LIVE 상태 점의 맥박 표시는 등재된 예외로 허용한다. (anti-ai-slop, CLAUDE.md §10)
- **FR-005**: 디자인 원본에 있으나 요구사항 ID가 배정되지 않은 섹션은 포팅하지 않아야 한다. 해당 섹션은 개구리 도감·무지개 개구리 도감, 획득 배지, 대왕 개구리 소환 게이지, 완주율 지표, 통합 검색창, 자기소개·관심 태그, 리더 완주율 패널, 주차별 커리큘럼, 모임 주기 표기, 개설 폼의 증빙 방식 선택기다. 근거는 §1.3 보류이거나 저장된 데이터가 없다는 것이다. 증빙 방식(`proof_type`)은 템플릿 정의의 `defaultProofType`에서 서버가 파생하고 개설 입력에 받는 필드가 없다 (`src/lib/validation.ts` `createPostSchema`).

**대시보드 피드 (req FR-013)**

- **FR-006**: 대시보드는 LIVE 핑 전광판, 마감 임박 단기 파티, 모집 중 정규 스터디, 아카이브(🏆명예의 전당 / 🪦Post-mortem), 성실 멤버 랭킹을 한 화면에 보여야 한다.
- **FR-007**: 정규 스터디 그리드는 최신순과 마감임박순을 유저가 고를 수 있어야 한다. 단기 파티는 마감 임박순으로, LIVE 핑은 유효한 것만 보여야 한다.
- **FR-008**: 카드는 제목, 태그, 모집 상태, 리더 핸들과 이니셜 뱃지, 현재/최대 인원을 보여야 한다. 정규 스터디는 기간과 사이클, 단기 파티는 남은 일수·마감일·장소, LIVE 핑은 내용·위치·남은 시간을 더한다. (prd F2)
- **FR-009**: 이니셜 뱃지는 핸들 앞 2자리를 쓰며 영문은 대문자로, 숫자·하이픈은 그대로 표기해야 한다. 외부 프로필 이미지를 불러오지 않는다. (CLAUDE.md §7.2)
- **FR-010**: 캠퍼스 뱃지는 캠퍼스가 비어 있지 않을 때만 렌더해야 하고, 비어 있을 때 빈 괄호·구분자 같은 흔적을 남기지 않아야 한다. (req FR-016)
- **FR-011**: 아카이브는 정규 스터디만 보여야 하며 단기 파티를 포함하지 않아야 한다. 🏆명예의 전당은 결과물 링크를, 🪦Post-mortem은 회고를 보여준다. (req FR-010, CLAUDE.md §7.2)
- **FR-012**: 성실 멤버 랭킹은 1~5위를 핸들·누적 완주 횟수·누적 리더 횟수와 함께 보여야 한다. 저장되지 않는 지표(완주율)를 표기하지 않는다.
- **FR-013**: LIVE 핑의 `[완료]`는 작성자 본인에게만 보여야 하고, 누른 즉시 전광판에서 사라져야 한다. (req FR-011)
- **FR-014**: 피드는 캠퍼스로 분리하거나 필터링하지 않아야 한다. 캠퍼스 필터 입구를 만들지 않는다. (CLAUDE.md §7.2)
- **FR-015**: 각 영역은 데이터가 없을 때 빈 상태 안내와 다음 행동(개설 입구)을 보여야 한다. (designs: `Dashboard.html` 점선 개설 카드)

**상세 모달과 참여 (req FR-013, FR-003)**

- **FR-016**: 카드의 `[상세보기]`는 상세 모달을 열어야 하며, 카드에서 곧바로 참여가 일어나서는 안 된다. (CLAUDE.md §6.2, prd §1.1)
- **FR-017**: 상세 모달은 비참여자에게 소개·기간·사이클·진행 방식·장소·참여자 목록·소통 플랫폼 종류·참고 링크를 보여야 한다.
- **FR-018**: 상세 모달은 비참여자에게 초대 링크를 노출하지 않아야 한다. 화면뿐 아니라 클라이언트로 전달되는 데이터에도 포함되지 않아야 한다. (헌법 V)
- **FR-019**: `[참여하기]`는 취소 불가와 외부 이동을 알리는 확인 팝업을 거쳐야 하며, 확정 전에는 어떤 기록도 남지 않아야 한다. (prd §1.1 2단계)
- **FR-020**: 확정 시 참여가 기록되고 인원이 갱신되며 새 탭으로 초대 링크가 열려야 한다. 확정 버튼은 처리 중 중복 입력을 받지 않아야 한다. (req FR-003)
- **FR-021**: 이미 참여한 유저에게는 링크 재열람 수단을 상시 제공해야 하며, 자진 참여 취소 수단을 제공하지 않아야 한다. (req §1.2)
- **FR-022**: 정원이 찬 글, 취소된 글, 완주 판정이 끝난 글은 참여 수단을 제공하지 않고 그 상태를 표시해야 한다. (req FR-004, NFR-003)
- **FR-023**: 리더 본인에게만 수정·취소 관리 입구를 보여야 한다. 화면에서 가리는 것은 보조이고, 거절은 서버가 한다. (req FR-017)
- **FR-024**: 요청이 거절되면 그 사유를 유저가 읽을 수 있는 한국어 문장으로 보여야 한다. 거절 코드(정원 초과·마감·권한 없음·상태 위반)별로 문장이 구분되어야 한다. (CLAUDE.md §8)

**개설 폼 (req FR-013, FR-001, FR-002, FR-011)**

- **FR-025**: 개설 화면은 유형(정규 스터디·단기 파티·LIVE 핑)에 따라 그 유형의 입력 항목만 보여야 한다.
- **FR-026**: 정규 스터디는 템플릿 6종 버튼으로 기본 제목·설명·태그를 채워야 하고, 채운 값은 유저가 수정할 수 있어야 한다. (req FR-002, FR-007)
- **FR-027**: 정규 스터디의 종료일은 읽기 전용 안내로 보여야 하고 유저가 지정할 수 없어야 한다. 단기 파티만 마감일을 직접 고른다. (CLAUDE.md §7.2)
- **FR-028**: LIVE 핑 폼은 한 줄 내용(최대 50자), 위치, 유효시간(30분·1시간·2시간·3시간) 3개만 받아야 한다. 정원·초대 링크·태그를 받지 않는다. (req FR-011)
- **FR-029**: 입력 제한(제목 40자, 설명 300자, 태그 3개, 정원 2~10, LIVE 내용 50자, 초대 링크 화이트리스트, 참고 링크 `https://`)은 보내기 전에 안내해야 한다. 프론트 검증은 보조이고 최종 방어선은 서버다. (CLAUDE.md §7.1)
- **FR-030**: LIVE 핑 하루 1회 제한에 걸린 유저에게는 이유를 안내하고 등록 입구를 비활성화해야 한다. (req FR-011)

**실시간 동기화 (req FR-014, NFR-004)**

- **FR-031**: 열려 있는 대시보드는 참여 인원 변화와 모집 상태 변화를 1초 안에 새로고침 없이 반영해야 한다. (req NFR-004)
- **FR-032**: 새 LIVE 핑은 1초 안에 전광판 맨 앞에 붙어야 하며, 알림에 실리지 않는 내용·위치는 조회로 보강해야 한다. (trd §5)
- **FR-033**: 조기 완료되거나 마감된 글은 열려 있는 화면에서 1초 안에 사라지거나 마감 상태로 바뀌어야 한다.
- **FR-034**: 실시간 경로로 초대 링크가 전달되지 않아야 한다. 공개 복제 컬럼은 최소 집합으로 유지한다. (trd §5, 헌법 V)
- **FR-035**: 실시간 연결이 없거나 끊겨도 화면은 조회 결과로 정상 동작해야 한다. 실시간은 보강이며 전제가 아니다.

**단기 파티 마감 (req FR-020)**

- **FR-042**: 마감일이 지난 단기 파티는 모집 피드에서 제외해야 한다. 상태값을 전이시키지 않고 만료 배치도 두지 않는다. 상세 조회는 계속 허용하며 마감 상태로 표시한다.
- **FR-043**: 마감일이 지난 단기 파티의 참여 요청은 거절해야 한다. 상태값이 모집 중으로 남아 있으므로 참여 경로에 마감일 검증을 따로 둔다.
- **FR-044**: 마감일이 지난 단기 파티는 아카이브(명예의 전당·Post-mortem)에 들어가지 않아야 하고 어떤 카운트도 가산하지 않아야 한다. (req FR-010, FR-020)
- **FR-045**: 완주 판정·회고 등록 화면은 이 범위에 없다. 아직 없는 화면으로 가는 입구를 노출하지 않아야 한다. (req FR-021)

**프로필 (req FR-019)**

- **FR-036**: 프로필은 GitHub 핸들, 이니셜 뱃지, 누적 완주 횟수, 누적 리더 횟수를 보여야 한다. 카운트는 완주 판정이 가산한 값을 그대로 읽는다.
- **FR-037**: 스터디 이력은 완주·리더·진행 중으로 구분해 참여 기록과 일치하게 보여야 한다. 신규 테이블·컬럼을 만들지 않는다. (req FR-019)
- **FR-038**: 프로필의 캠퍼스 뱃지는 캠퍼스가 있을 때만 렌더해야 하고 기수는 표기하지 않아야 한다. (req FR-016, §1.3)

**접근 경로**

- **FR-039**: 사이드바는 대시보드·정규 스터디·단기 파티·아카이브 이동과 프로필 입구를 제공해야 한다. (designs: `Dashboard.html`)
- **FR-040**: 비로그인 상태에서 보호 화면에 들어오면 로그인이 필요하다는 안내를 보여야 한다. Phase 3에는 개발용 Mock 전환 입구를 함께 둔다. 랜딩 게이트는 Phase 4다. (req FR-015)
- **FR-041**: 개발용 Mock 전환 입구는 개발 환경에서만 보여야 하고 상용 빌드에서 노출되지 않아야 한다. (CLAUDE.md §6.1)

### Key Entities

- **피드 항목(카드)**: 글 하나를 카드로 줄인 표현. 유형에 따라 보여줄 값이 다르다 — 정규 스터디는 기간·사이클, 단기 파티는 남은 일수·마감일, LIVE 핑은 남은 시간·위치. 어떤 유형이든 초대 링크를 갖지 않는다.
- **상세 보기**: 글 하나의 전체 표현. 참여 여부에 따라 초대 링크의 유무가 갈리는 유일한 표현이며, 비참여자 데이터에는 그 필드가 존재하지 않는다.
- **참여 확정 의사**: `[참여하기]`와 `[확인]` 사이의 중간 상태. 저장되지 않으며, 확정 전에 떠나면 흔적이 남지 않는다.
- **실시간 변경 알림**: 글의 인원·상태·만료 시각 변화와 새 글 등장만 담은 최소 정보. 제목·위치·초대 링크를 담지 않으므로 화면에 그리기 전 조회로 보강해야 한다.
- **스터디 이력 항목**: 유저가 참여한 글 하나를 완주·리더·진행 중 중 하나로 분류한 표현. 참여 기록과 글 상태에서 파생되며 따로 저장되지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 로그인한 유저가 대시보드를 열어 참여까지 끝내는 데 클릭 3번(상세보기 → 참여하기 → 확인) 이내로 도달하고, 중간에 다른 화면으로 이동하지 않는다.
- **SC-002**: 비참여자에게 초대 링크가 노출되는 경로가 0건이다 — 화면, 클라이언트로 전달되는 데이터, 실시간 알림 전부를 확인한다.
- **SC-003**: 다른 세션의 참여·LIVE 핑 등록·조기 완료가 열려 있는 대시보드에 1초 안에 반영된다 (측정 10회 중 10회).
- **SC-004**: 네 영역(LIVE 핑·단기 파티·정규 스터디·아카이브)의 정렬·필터 결과가 조회 기준과 100% 일치하고, 만료된 LIVE 핑과 취소된 글이 피드에 0건 노출된다.
- **SC-005**: 캠퍼스가 비어 있는 유저의 카드·상세·프로필에서 뱃지 자리가 깨진 표기(빈 괄호·고아 구분자) 없이 렌더되는 비율 100%.
- **SC-006**: 제한을 넘는 입력(제목 41자, 설명 301자, 태그 4개, 정원 1·11명, LIVE 내용 51자, 화이트리스트 밖 링크)이 글 생성으로 이어지는 경우가 0건이고, 각 경우에 유저가 읽을 수 있는 거절 사유가 보인다.
- **SC-007**: 프로필의 누적 완주·리더 횟수가 완주 판정 결과와 일치하고, 이력 목록이 참여 기록과 1:1로 맞는다.
- **SC-008**: 화면 폭 375px에서 가로 페이지 스크롤이 발생하지 않고, 각 영역이 1열로 접힌다.
- **SC-009**: 디자인 자가 점검 6항목(그라데이션·컬러 그림자·호버 이동·배경 장식·순수 장식·기본 폰트 수렴)에 걸리는 항목이 0건이다.
- **SC-010**: 기존 테스트 전건과 `lint`·`typecheck`·`build`가 통과하고, 이 브랜치가 추가한 도메인 경로의 테스트도 통과한다.
- **SC-011**: 마감일이 지난 단기 파티가 모집 피드에 0건 노출되고, 그 파티에 참여가 성립하는 경우가 0건이다 (TC-PARTY-01·02 통과).

## Assumptions

- **요구사항 ID 배정은 `docs/requirement.md` §2를 따른다.** 입력에 적힌 "FR-014(상세보기 모달)"는 실제로 `FR-013`의 범위이며, `FR-014`는 Realtime이다. `create_study.html` 포팅도 `FR-013`에 포함되므로 이 브랜치 범위에 넣는다.
- 화면은 Phase 1~2에서 만든 조회·변경 경로를 그대로 쓴다. 저장 구조(테이블·컬럼)를 바꾸지 않는다 (req FR-019).
- 카드와 상세에 리더의 누적 리더 횟수·완주율을 표기하지 않는다. 디자인 원본에는 있으나 화면 명세(prd F2·F4)의 표출 항목에 없고, 표기하려면 조회 응답에 유저 통계 필드를 더해야 한다. 지금은 응답 표면을 늘리지 않는 쪽을 고른다.
- 사이클 표기는 종료일에서 파생한다. 저장된 사이클 컬럼은 어느 경로에서도 채워지지 않으므로 화면이 그 값을 읽지 않는다.
- 주소 체계는 보호 화면을 `/dashboard`·`/create`·`/profile`로 두고 루트는 대시보드로 보낸다. Phase 4의 랜딩 게이트가 같은 주소를 보호 대상으로 전제하므로(trd §2.2), 지금 다른 주소를 쓰면 Phase 4에서 다시 옮겨야 한다.
- 인증은 Phase 3 그대로 개발용 Mock 세션이다. GitHub 로그인·랜딩·세션 쿠키는 `FR-015`(Phase 4)이며 이 브랜치에서 만들지 않는다. 외부 선행 작업 U7(OAuth App 등록)은 이 브랜치의 선행 조건이 아니다.
- 실시간 공개 복제 컬럼은 이미 최소 집합으로 등록돼 있다(외부 선행 작업 U2 완료). 이 브랜치는 그 구성을 바꾸지 않는다.
- 공개 키 형식(`sb_publishable_`)이 설치된 클라이언트 라이브러리에서 동작하는지는 구독을 붙이는 단계에서 확인한다 (next-steps U3 메모).
- 실시간 검증 작업은 작업 목록의 마지막 단계에 둔다. 화면 포팅은 실시간 없이 진행되므로 순서를 섞으면 불필요하게 막힌다 (next-steps §3).
- 단기 파티의 "전체 보기", 정규 스터디 전용 목록 화면 같은 사이드바 하위 화면은 대시보드의 같은 데이터를 유형으로 좁혀 보여주는 화면으로 본다. 새 조회 규칙을 만들지 않는다.
- 디자인 원본은 정적으로 렌더된 결과물이다. 호버·누름 값의 원본은 `docs/designs/interactions.md`이며, 원본 HTML에서 지워진 상호작용을 추측해 복원하지 않는다.
- 확인 팝업 문구는 화면 명세의 문장을 그대로 쓴다 — "정말 참여하시겠습니까? 참여 후에는 취소가 불가능하며 오픈채팅방으로 이동합니다." (prd §1.1)
- 시연용 시드 데이터 주입(prd §4-2)은 이 브랜치의 범위가 아니다. 빈 상태 렌더(FR-015)로 빈 화면 문제를 막는다.
- 단기 파티 마감은 Lazy Filter로 처리한다. 상태값을 바꾸는 배치를 두지 않는 쪽을 고른 이유는 LIVE 핑 만료가 이미 같은 방식으로 동작해 검증된 경로이고, 배치를 두면 운영 인프라와 배포 연결(U4)에 묶이기 때문이다. 이 결정으로 `docs/requirement.md`(FR-020·TC-PARTY-01·02), `CLAUDE.md` §6.4, `docs/prd.md` §1-5·F5를 같은 브랜치에서 함께 고쳤다.
- 완주 판정·회고 등록 화면을 분리한 이유는 PR 크기와 검증 순서다. 006은 모집·참여·실시간 루프를 닫는 데 집중하고, 리더 액션(수정·취소·판정·회고)은 한 화면 묶음으로 007에서 포팅한다. 006에서 만드는 상세 모달의 리더 입구는 수정·취소까지만 연결한다.
